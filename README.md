# Verde Marea

Verde Marea — локальный проект системы бронирования столов средиземноморского ресторана для финального задания Яндекс Практикума. Гость проверяет свободное время, пользователь бронирует стол, а сотрудники управляют бронями и расписанием.

[Репозиторий на GitHub](https://github.com/alpobaggins/verde-marea)

Стек проекта — Next.js (App Router), React, TypeScript, Tailwind CSS v4, Prisma ORM с адаптером PostgreSQL, Zod, bcryptjs и ESLint.

## Возможности по ролям

| Роль | Возможности |
| --- | --- |
| Гость | Просмотр информации о ресторане и доступных окон, регистрация и вход |
| Пользователь | Создание брони, просмотр своих броней и уведомлений, отметка о прочтении, отмена своей активной брони не позднее чем за три часа |
| Администратор | Возможности пользователя для собственных броней, управление статусами броней, закрытиями и доступностью столов, просмотр списка обычных пользователей и разрешённых событий аудита |
| Суперадминистратор | Возможности администратора, просмотр всех аккаунтов и событий аудита, назначение и отзыв роли администратора у других аккаунтов |

## Локальный запуск

Понадобятся Node.js 24 с npm и запущенный PostgreSQL 16 с клиентскими утилитами `createdb` и `psql`. Проверено на Node.js 24.22.2, npm 11.19.1 и PostgreSQL 16.15. Для первоначальной установки нужен доступ к npm-реестру или заполненный кэш npm.

Все команды выполняются из корня полученной копии репозитория.

1. Установи зависимости по lockfile.

   ```sh
   npm ci
   ```

2. Создай отдельную локальную базу и скопируй шаблон окружения. Подставь свою роль PostgreSQL вместо `YOUR_DB_USER`. Если у роли нет права создавать базы, попроси локального администратора создать базу с этой ролью в качестве владельца. При другом порте добавь `-p <порт>` к `createdb` и укажи этот порт в `DATABASE_URL`.

   ```sh
   createdb -h 127.0.0.1 -U YOUR_DB_USER verde_marea_dev
   cp -i .env.example .env
   ```

   Заполни локальный `.env`. Для специальных символов в пароле PostgreSQL используй percent-encoding. Храни `.env` вне Git.

   | Переменная | Назначение |
   | --- | --- |
   | `DATABASE_URL` | URL отдельной базы PostgreSQL с реквизитами локальной роли |
   | `RESTAURANT_TIME_ZONE` | Часовой пояс расписания, по умолчанию `Europe/Moscow` |
   | `SEED_USER_PASSWORD` | Пароль демонстрационного пользователя |
   | `SEED_ADMIN_PASSWORD` | Пароль демонстрационного администратора |
   | `SEED_SUPER_ADMIN_PASSWORD` | Пароль демонстрационного суперадминистратора |

3. Сгенерируй Prisma Client, примени миграции и заполни базу демонстрационными данными.

   ```sh
   npm exec -- prisma generate
   npm exec -- prisma migrate deploy
   npm exec -- prisma db seed
   npm exec -- prisma migrate status
   ```

4. Запусти сервер после успешного выполнения этих команд.

   ```sh
   npm run dev -- --webpack
   ```

   Открой [http://localhost:3000](http://localhost:3000).

### Демонстрационные аккаунты

После seed войди через `/login` с паролем, который указал для нужной роли в своём `.env`.

| Роль | Email | Переменная пароля |
| --- | --- | --- |
| `user` | `user@verde-marea.test` | `SEED_USER_PASSWORD` |
| `admin` | `admin@verde-marea.test` | `SEED_ADMIN_PASSWORD` |
| `super_admin` | `super-admin@verde-marea.test` | `SEED_SUPER_ADMIN_PASSWORD` |

Seed предназначен для локальной демонстрации. При повторном запуске существующие аккаунты сохраняют роли и пароли. Для одновременной проверки разных ролей используй отдельные профили браузера. Обычный пользователь из seed подходит для сценария входа, а для проверки регистрации и смены роли создай отдельный аккаунт.

### Обновление и сброс базы

Используй [инструкцию безопасного обновления](prisma/README.md#безопасное-обновление) после изменений схемы или серверной логики. Для повторной демонстрации есть [сброс одноразовой базы](prisma/README.md#сброс-одноразовой-демонстрационной-базы). Сброс удаляет все данные выбранной схемы.

## Авторизация

На странице `/register` укажи имя, email и пароль. После регистрации войди на `/login`. Страница `/account` показывает email и позволяет завершить текущую сессию. Для входа также подходят локальные аккаунты из seed.

Email очищается от пробелов по краям и приводится к нижнему регистру. Поддерживаются непустые пароли длиной до 72 байт UTF-8. Сессия действует семь суток с момента входа. Production-cookie требует HTTPS.

Страница `/admin` доступна для `admin` и `super_admin`. Обработчик `GET /api/admin/access` проверяет сессию и роль при каждом запросе. Он возвращает только текущую роль сотрудника, а при отказе отвечает `401` или `403`.

Защищённая страница кабинета получает аккаунт из `requireSignedInUser()`. Административная страница проверяет роль, а API независимо проверяют сессию и полномочия при каждом запросе. Критические операции повторно проверяют права и актуальное состояние ресурса внутри транзакции.

### Браузерные сценарии кабинета и панели

- `/account` показывает предстоящие и текущие брони, историю и внутренние уведомления. Отмена требует подтверждения, а отметка о прочтении обновляется после сохранения. Время отображается в зоне ресторана, по умолчанию московской.
- `/admin` показывает список бронирований с фильтрами по дате и статусу. В деталях можно выбрать допустимый переход, ввести причину и подтвердить действие.
- `/admin?section=availability` показывает график, закрытия и столы. Можно добавить закрытие целого дня или штатного окна, снять исключение, отключить или включить стол.
- `/admin?section=users` показывает доступные по роли аккаунты. Только `super_admin` может назначить или отозвать роль `admin` после подтверждения.
- `/admin?section=audit` показывает события от новых к старым. Доступны фильтры по действию и объекту, лимит выдачи и раскрытие изменений. Исходная причина видна только `super_admin`.

После ответа `409` интерфейс показывает причину конфликта и перечитывает затронутые данные. На узком экране служебные таблицы прокручиваются внутри подписанных областей, доступных с клавиатуры.

Команда `npm run test:auth` запускает тесты валидации, сессий и правил доступа. Для тестов с PostgreSQL задай `AUTH_TEST_DATABASE_URL` для отдельной тестовой базы с применёнными миграциями. Для HTTP-теста также задай `AUTH_TEST_APP_URL` с адресом запущенного приложения, подключённого к этой же тестовой базе. Тесты удаляют созданные ими аккаунты и сессии.

### Строгая проверка перед сдачей

Используй отдельные пустые базы PostgreSQL и примени к каждой обе миграции
без seed. Используй отдельный тестовый кластер или отдельные тестовые базы,
а `verde_marea_dev` оставь для локальной демонстрации. Некоторые наборы
очищают свои тестовые таблицы и временно добавляют ограничения и триггеры.
Для каждого набора назначь отдельную базу и передай её URL через переменную
окружения. Например, для набора бронирований выполни:

```sh
DATABASE_URL="${BOOKING_TEST_DATABASE_URL:?Укажи URL тестовой базы}" npm exec -- prisma migrate deploy
```

Префиксы в таблице дополняются суффиксами `_DATABASE_URL` и `_APP_URL`.

| Префикс | База |
| --- | --- |
| `AUTH_TEST` | `verde_marea_auth_test` |
| `AVAILABILITY_TEST` | `verde_marea_availability_test` |
| `BOOKING_TEST` | `verde_marea_booking_test` |
| `ACCOUNT_TEST` | `verde_marea_account_test` |
| `ADMIN_BOOKING_TEST` | `verde_marea_admin_booking_test` |
| `ADMIN_AVAILABILITY_TEST` | `verde_marea_admin_availability_test` |
| `ADMIN_IDENTITY_TEST` | `verde_marea_admin_identity_test` |

После сборки Webpack запусти для каждого набора отдельный локальный сервер
через `npm start -- -H 127.0.0.1 -p <порт>` с `DATABASE_URL` этой тестовой
базы. Укажи его адрес в соответствующем `_APP_URL`. Для
`AVAILABILITY_TEST` достаточно URL базы. URL тестовых баз передаются
без параметров строки запроса. Установи `RESTAURANT_TIME_ZONE=Europe/Moscow`
для серверов и прогона.

```sh

```

Команда проверяет конфигурацию всех семи наборов перед запуском и
завершается ошибкой при пропуске любого теста. Отдельные команды
`npm run test:…` сохраняют быстрый режим с пропуском проверок,
для которых не настроено окружение.

## Чек-лист локальной приёмки

Используй отдельную демонстрационную базу с seed. Строгий прогон выполняется на семи других пустых базах без seed.

- [ ] [Подготовь окружение и запусти приложение](#локальный-запуск). До запуска сгенерируй Prisma Client, примени обе миграции и выполни seed. Проверь актуальность схемы через `prisma migrate status`, наличие трёх демонстрационных ролей и открытие `/booking`.
- [ ] Как гость найди открытое окно. Зарегистрируй нового пользователя в `/register`, войди в `/login`, создай бронь и проверь статус `pending` в `/account`.
- [ ] В профиле администратора открой `/admin`, отфильтруй список броней и подтверди заявку. В кабинете владельца проверь статус `confirmed` и уведомление. Отметь его прочитанным и проверь отметку после обновления.
- [ ] Для окна с запасом более трёх часов проверь отмену владельцем. Бронь должна остаться в истории, а окно снова появиться в доступности, если нет других ограничений. Для проверки конфликта создай новую бронь, оставь открытой её карточку со статусом `pending`, подтверди бронь администратором и попробуй отменить её из старой карточки. Кабинет должен показать конфликт и обновить статус.
- [ ] В разделе доступности администратора закрой свободное окно или день и проверь публичный поиск. Сними закрытие и проверь восстановление окна. Отключи и снова включи стол, у которого нет активных будущих броней.
- [ ] В профиле суперадминистратора назначь новому аккаунту роль `admin`, а затем отзови её. После каждого изменения обнови административную страницу в профиле этого аккаунта и проверь доступ с той же сессией.
- [ ] В журнале суперадминистратора найди события бронирования, изменения доступности и смены роли. Проверь исполнителя, объект и значения до и после. В журнале обычного администратора проверь, что события смены ролей исключены.
- [ ] Выполни TypeScript, ESLint, сборку Webpack и [строгий прогон](#строгая-проверка-перед-сдачей) без пропусков. Проверь состав файлов перед публикацией. Локальные настройки, зависимости, сборки и временные файлы храни вне Git.

## API доступности

Любой посетитель может вызвать `GET /api/availability?date=2026-11-24&guests=2`.
`date` — календарная дата ресторана в формате `YYYY-MM-DD`, `guests` —
положительное целое число. `RESTAURANT_TIME_ZONE` задаёт зону расписания.
По умолчанию используется `Europe/Moscow`.

Пример ответа `200 OK` для даты в пределах горизонта, когда свободно одно окно:

```json
{
  "status": "available",
  "slots": [
    { "startsAt": "2026-11-24T09:00:00.000Z", "endsAt": "2026-11-24T10:30:00.000Z" }
  ]
}
```

Границы окна передаются в ISO 8601 в UTC. В примере это 12:00–13:30 по Москве.
Ответы `200 OK` с пустым `slots` содержат один из следующих статусов.

| Статус | Значение |
| --- | --- |
| `closed` | Понедельник или закрытия перекрывают все оставшиеся окна |
| `outside_horizon` | Дата раньше сегодняшней или позже 13-й календарной даты после неё |
| `no_availability` | Будущих окон либо свободных столов нужной вместимости нет |

Некорректные параметры возвращают `400 Bad Request` со статусом `invalid_input`
и текстовым полем `error`. Ответы не кэшируются. Доступность предварительная.
При создании брони сервер повторяет проверку в транзакции `Serializable`.

Для интеграционных тестов доступности примени обе миграции к отдельной пустой
`verde_marea_availability_test` без seed. Передай её URL через
`AVAILABILITY_TEST_DATABASE_URL` и запусти `npm run test:availability`.
Записи интеграционного расчёта откатываются, а временный стол HTTP-обработчика
удаляется после проверки. Без переменной выполняются проверки календаря
и API, которым не требуется PostgreSQL. Для проверки часового пояса процесса
запусти команду с `TZ=America/Los_Angeles`.

## API создания бронирования

`POST /api/bookings` требует действующую cookie сессии и
`Content-Type: application/json`. Получи окна через API доступности и передай
`startsAt` выбранного окна в UTC вместе с датой ресторана и числом гостей.

```sh
curl -i http://localhost:3000/api/bookings \
  --cookie "verde_session=${SESSION_TOKEN}" \
  --header 'Content-Type: application/json' \
  --data '{"date":"2026-11-24","startsAt":"2026-11-24T09:00:00.000Z","guests":2}'
```

Для запроса под локальным сервером разработки возьми cookie из действующей
сессии. Production использует `__Host-verde_session` и HTTPS для браузера.
Выбранная дата должна быть в текущем горизонте. Пример ответа `201 Created`:

```json
{
  "id": "b870d270-e9bc-4320-a0b4-ad85d73e64dc",
  "startsAt": "2026-11-24T09:00:00.000Z",
  "endsAt": "2026-11-24T10:30:00.000Z",
  "guestCount": 2,
  "status": "pending"
}
```

| HTTP | Условие |
| --- | --- |
| `400` | Некорректный JSON, значения или дополнительные поля |
| `401` | Сессия отсутствует, истекла или отозвана |
| `409` | Окно недоступно, пересекается с активной бронью владельца или исчерпан лимит повторов |
| `500` | Непредвиденная серверная ошибка |

Ошибки возвращают JSON с полем `error`. При `409` можно заново запросить
доступность. Сервер выбирает стол и атомарно записывает бронь, аудит и
внутреннее уведомление.

Для интеграционных тестов создания примени обе миграции к отдельной пустой
`verde_marea_booking_test` без seed. Собери приложение командой
`npm run build -- --webpack` и запусти production-сборку с `DATABASE_URL`,
указывающим на эту базу. Передай тот же URL базы через
`BOOKING_TEST_DATABASE_URL`, адрес сервера через `BOOKING_TEST_APP_URL` и запусти
`npm run test:booking`. Используй зону `Europe/Moscow` на сервере и в тестах.
Без этих переменных выполняются проверки входной схемы и трёхчасовой границы отмены.

## API отмены бронирования

`PATCH /api/bookings/{id}/cancel` использует действующую cookie сессии и
UUID бронирования в пути. Передай в JSON поле `expectedStatus` со статусом,
который владелец видел в карточке. Параметры строки запроса не передаются.
Владелец может отменить бронь в статусе `pending` или `confirmed`, если до
начала осталось не менее трёх часов.

```sh
curl -i -X PATCH "http://localhost:3000/api/bookings/${BOOKING_ID}/cancel" \
  --cookie "verde_session=${SESSION_TOKEN}" \
  --header 'Content-Type: application/json' \
  --data '{"expectedStatus":"pending"}'
```

Пример ответа `200 OK`:

```json
{
  "id": "b870d270-e9bc-4320-a0b4-ad85d73e64dc",
  "startsAt": "2026-11-24T09:00:00.000Z",
  "endsAt": "2026-11-24T10:30:00.000Z",
  "guestCount": 2,
  "status": "cancelled"
}
```

| HTTP | Условие |
| --- | --- |
| `400` | Некорректный запрос, недопустимый статус или до начала меньше трёх часов |
| `401` | Нет действующей сессии |
| `404` | Бронирование отсутствует или принадлежит другому владельцу |
| `409` | Текущий статус отличается от `expectedStatus` или исчерпан лимит повторов |
| `500` | Непредвиденная серверная ошибка |

Ошибки возвращаются в поле `error`. После успешной отмены бронь остаётся в
истории, а стол становится доступным по общим правилам. Повтор запроса с
прежним статусом возвращает `409` без новых событий. При `409` кабинет
сообщает об изменении и обновляет данные бронирований. Интеграционные
проверки отмены входят в `npm run test:booking` и используют то же тестовое
окружение, что и создание.

## Пользовательский сценарий

1. Открой главную страницу и перейди в **Забронировать стол** (`/booking`).
2. Выбери дату и количество гостей, затем нажми **Найти свободное время**.
   Время окон отображается по Москве при настройках MVP.
3. Выбери окно. Если нужна сессия, открой **Войти для бронирования**. Можно
   зарегистрироваться с этой страницы. После входа приложение вернёт тебя
   к форме бронирования, где нужно заново выбрать дату, гостей и окно.
4. Нажми **Забронировать**. Подтверждение появится после ответа сервера.
   Если окно уже занято, форма сохранит дату и гостей, обновит доступность
   и предложит выбрать окно заново.
5. Открой **Личный кабинет** (`/account`). Там видны предстоящие и текущие
   бронирования, история и внутренние уведомления.
6. В доступной для отмены брони нажми **Отменить бронь** и подтверди действие.
   Бронь переместится в историю со статусом **Отменена**, а стол снова можно
   будет забронировать при отсутствии других ограничений.
7. Нажми **Отметить прочитанным** у уведомления. После обновления оно
   останется в списке с отметкой **Прочитано**.

`PATCH /api/notifications/{id}/read` требует действующую cookie сессии и UUID
в пути. Передавать тело и параметры запроса не нужно. Для своего уведомления
возвращается `204`, в том числе при повторе с сохранением исходного времени
прочтения. Без сессии возвращается `401`, для чужого или отсутствующего
уведомления — одинаковый `404`.

Для интеграционных тестов кабинета примени миграции к отдельной пустой базе
`verde_marea_account_test` и запусти production-сборку с её `DATABASE_URL`.
Передай этот же URL через `ACCOUNT_TEST_DATABASE_URL` и адрес сервера через
`ACCOUNT_TEST_APP_URL`, затем выполни `npm run test:account`. Без этих
переменных запускается только проверка московского календаря. Чтобы проверить
независимость времени от зоны процесса, запусти сервер и тест с
`TZ=America/Los_Angeles` и `RESTAURANT_TIME_ZONE=Europe/Moscow`.

## API управления бронированиями

Все запросы используют действующую cookie сессии. Доступ имеют
`admin` и `super_admin`. Ответы содержат номер брони, начало и конец
окна в UTC, число гостей, статус, имя клиента и обозначение стола.
Ответы с административными данными имеют `Cache-Control: private, no-store`.

| HTTP-запрос | Результат |
| --- | --- |
| `GET /api/admin/bookings` | Объект `{ bookings: [...] }` со списком, отсортированным по началу окна, затем по ID |
| `GET /api/admin/bookings?date=2026-11-24&status=pending` | Список с фильтрами по календарной дате начала в зоне ресторана и по статусу. Фильтры независимы и необязательны |
| `GET /api/admin/bookings/{id}` | Сведения о брони по UUID |
| `PATCH /api/admin/bookings/{id}` | Новый статус и сведения о брони. Тело запроса передаётся как `application/json` |

Для смены статуса передай прочитанный ранее `expectedStatus`, целевой
`status` и при необходимости `reason`. Пример тела запроса для отмены
подтверждённой брони:

```json
{ "expectedStatus": "confirmed", "status": "cancelled", "reason": "Ресторан закрыт" }
```

| Переход | Условие |
| --- | --- |
| `pending` → `confirmed` | До начала окна |
| `pending` или `confirmed` → `cancelled` | До начала окна, обязательна непустая причина |
| `pending` → `completed` | После окончания окна, визит состоялся, обязательна непустая причина |
| `confirmed` → `completed` | После окончания окна, визит состоялся |
| `pending` или `confirmed` → `no_show` | После окончания окна, визит не состоялся |

При фиксации результата визита сотрудник выбирает `completed` или
`no_show` по факту посещения. Сервер проверяет время и статус и сохраняет
изменение, аудит с актуальной ролью инициатора и уведомление владельца
в одной транзакции `Serializable`.

Успешный запрос возвращает `200`. Ошибки содержат поле `error`.
`400` означает неверный запрос или запрещённый переход, `401` —
отсутствие действующей сессии, `403` — недостаточные права, `404` —
отсутствие брони, `409` — изменившийся статус или неразрешившийся
конфликт записи. При `409` заново открой сведения о брони перед
следующим действием.

Для `npm run test:admin-booking` примени миграции к отдельной пустой
PostgreSQL 16 с именем `verde_marea_admin_booking_test`. Запусти
production-сборку с URL этой базы в `DATABASE_URL` и с зоной ресторана
`Europe/Moscow`. Передай тестам тот же URL в
`ADMIN_BOOKING_TEST_DATABASE_URL` и адрес сервера в
`ADMIN_BOOKING_TEST_APP_URL`.

## API управления доступностью

Для всех административных операций нужна cookie действующей сессии
`admin` или `super_admin`. Ответы API закрытий и столов имеют
`Cache-Control: private, no-store`. Запросы на изменение передают тело
с `Content-Type: application/json`.

| HTTP-запрос | Вход и результат |
| --- | --- |
| `GET /api/admin/availability/closures` | `200`, объект `{ closures: [...] }`. Закрытия упорядочены по началу и ID |
| `POST /api/admin/availability/closures` | `{ "kind": "day", "date": "2026-11-24" }` или `{ "kind": "window", "date": "2026-11-24", "start": "12:00" }`. Ответ `201` содержит созданное закрытие |
| `DELETE /api/admin/availability/closures/{id}` | Тело с `kind`, `startsAt` и `endsAt` из полученного закрытия. Ответ `204` |
| `GET /api/admin/availability/tables` | `200`, объект `{ tables: [...] }`. Столы упорядочены по обозначению, выдаются `id`, `label`, `capacity`, `isAvailable` |
| `PATCH /api/admin/availability/tables/{id}` | `{ "isAvailable": false }` для отключения, `true` для включения. Ответ `200` содержит обновлённый стол |

Дата и время начала относятся к зоне ресторана (`Europe/Moscow` по
умолчанию). В ответе границы закрытия передаются в UTC с миллисекундами.
День закрывается от местной полуночи до следующей полуночи. Для окна
выбирается один штатный старт рабочего дня с 12:00 до 19:30 с шагом
90 минут. Поле причины для закрытия в MVP не предусмотрено.

Точный дубликат отклоняется. Закрытие дня может перекрывать закрытие
окна. При снятии удаляется ровно одно исключение по ID и ожидаемым
границам и виду. Остальные ограничения продолжают действовать.
Закрытие или отключение стола отклоняется, если затрагивает будущую
бронь в `pending` или `confirmed`. Существующие брони и их столы
сохраняются. Включение стола возвращает его в подбор с учётом графика,
закрытий и занятости. Изменения действуют для следующих запросов
публичной доступности и нового бронирования сразу после коммита транзакции.

Статусы ошибок: `400` для некорректного запроса, `401` без действующей
сессии, `403` при недостаточной роли, `404` для отсутствующего стола и
`409` при конфликте с бронью, точном дубликате, повторном переключении,
устаревших данных или конкурентном изменении. Каждая успешная операция
изменения пишет аудит в той же транзакции `Serializable`.

## API пользователей и журнала аудита

Запросы используют действующую cookie сессии. Ответы имеют
`Cache-Control: private, no-store`.

| HTTP-запрос | `admin` | `super_admin` |
| --- | --- | --- |
| `GET /api/admin/users` | Список аккаунтов с ролью `user` | Список всех аккаунтов с текущей версией роли |
| `PATCH /api/admin/users/{id}/role` | `403` | Смена роли другого аккаунта между `user` и `admin` |
| `GET /api/admin/audit` | События бронирований, закрытий и доступности столов | Все виды событий |

`GET /api/admin/users` возвращает `{ users: [...] }`. Поля аккаунта —
`id`, `name`, `email`, `role`, а для `super_admin` также `roleVersion`.
Список отсортирован по имени и ID и выдаётся целиком.

Для смены роли передай UUID аккаунта и тело с `Content-Type: application/json`.
Укажи текущие `expectedRole` и `expectedVersion` из списка и целевую роль `role`:

```json
{ "expectedRole": "user", "expectedVersion": 0, "role": "admin" }
```

Версия увеличивается с каждой успешной сменой роли. Она позволяет
отклонить старый запрос, даже если роль успела вернуться к прежнему
значению. Успешный запрос возвращает `200` и обновлённый аккаунт.
Смена роли и запись аудита выполняются атомарно в `Serializable`.
Сессии сохраняются и при каждом защищённом запросе получают актуальную
роль. После понижения та же cookie сразу теряет доступ к административным API,
а личный кабинет остаётся доступен.

`GET /api/admin/audit` возвращает `{ events: [...] }` от новых событий к
старым с дополнительной сортировкой по ID при одинаковом времени.
Доступны необязательные фильтры `action` и `targetType` по перечислениям
модели Prisma и `limit` от 1 до 100 (по умолчанию 50). Событие содержит
ID, время, тип действия, тип и ID объекта, роль исполнителя на момент
действия, разрешённые значения `before` и `after` и поле `actor` с
ID и именем исполнителя. Для `admin` поле `actor` равно `null`, если
исполнитель имел привилегированную роль на момент события или имеет её
сейчас. `admin` получает только `hasReason`. `super_admin` получает
исходный текст `reason` или `null`. Журнал доступен только для чтения.

Гость получает `401`, пользователь без административных полномочий —
`403`. Ошибки формата возвращают `400`, при смене роли по корректному UUID
несуществующего аккаунта возвращается `404`, устаревшие данные или конкурентный конфликт —
`409`, ошибка сервера — `500`.
