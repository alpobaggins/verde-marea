# Модель данных Verde Marea

Архитектура согласована на подэтапе 2.1. Бизнес-правила и матрица доступа закреплены в [spec.md](../spec.md). Здесь описано их отображение в PostgreSQL 16 и Prisma.

## Сущности и ограничения

| Модель | Назначение и поля | Связи и ключи | Индексы |
| --- | --- | --- | --- |
| `User` | Имя, email, `passwordHash`, роль `Role`, дата создания. Роль по умолчанию — `user` | PK `id`. Уникальный `email`. Сервер одинаково нормализует email при регистрации и входе. Один аккаунт имеет много броней и может быть инициатором многих записей аудита | PK, уникальный индекс email |
| `Session` | SHA-256-хеш токена `tokenHash`, владелец `userId`, срок `expiresAt`. Сервер проверяет срок и читает текущую роль из связанного аккаунта | PK `tokenHash` типа `char(64)`. FK на `User` | PK, индекс `userId` |
| `Table` | Уникальная метка, вместимость, признак доступности. Стол выводится из доступности без удаления | PK `id`. Один стол связан со многими бронями | Уникальный индекс `label`, составной индекс `isAvailable, capacity, id` для подбора |
| `Booking` | Начало, конец, число гостей, статус `BookingStatus`, время создания и изменения | PK `id`. Обязательные FK на владельца и назначенный стол. Уникальная пара `id, userId` служит целью FK уведомления. Бронь сохраняется после отмены | `userId, startsAt` для истории и проверки владельца, `tableId, startsAt` для занятости, `startsAt` для административного списка и закрытий всего ресторана |
| `Notification` | Снимок статуса на момент события, дата создания, необязательная дата прочтения | PK `id`. FK `bookingId, recipientId` на `Booking(id, userId)` не позволяет сохранить уведомление для чужой брони. Пара `bookingId, status` уникальна, так как машина состояний допускает один вход в каждый статус | `recipientId, createdAt` для ленты владельца |
| `AuditLog` | Актор, снимок его роли, действие, тип и ID объекта, изменённые поля до и после в JSON, причина, время | PK `id`. Обязательный FK на актора. У цели полиморфная ссылка `targetType, targetId` без FK. Запись остаётся читаемой и после снятия закрытия | `createdAt`, `actorId, createdAt`, `targetType, targetId, createdAt` |
| `AvailabilityClosure` | Исключение для всего ресторана. Вид `day` или `window`, начало, конец, время создания | PK `id`. Пара `startsAt, endsAt` уникальна. При снятии закрытия строка удаляется, а снимок остаётся в аудите | Составной уникальный индекс `startsAt, endsAt` |

Идентификаторы сущностей хранятся как UUID, моменты времени — как `timestamptz(3)`. У сессии первичный ключ — хеш токена. Бронь хранит обе границы для прямой проверки пересечений. `Role` и `BookingStatus` соответствуют спецификации. `ClosureKind` отличает закрытый день от отдельного окна. `AuditAction` и `AuditTarget` задают значения для фильтров журнала. Связи броней, уведомлений и аудита используют `Restrict` при удалении и изменении ключа. FK `Session.userId` использует `Cascade` для обеих операций. Через приложение аккаунты, столы, брони, уведомления и события аудита сохраняются. Отмена меняет статус брони, отметка о прочтении обновляет уведомление, отключение стола меняет его доступность. При выходе удаляется текущая сессия, при снятии закрытия — выбранное исключение. Истёкшие сессии отклоняются при чтении. Журнал пишется только вместе с исходной операцией. В его выдаче действуют ограничения по роли из спецификации.

### SQL CHECK в начальной миграции

| Таблица | Выражение CHECK |
| --- | --- |
| `Table` | `"capacity" > 0` |
| `Booking` | `"guestCount" > 0` |
| `Booking` | `"endsAt" > "startsAt"` |
| `Booking` | `"endsAt" - "startsAt" = interval '90 minutes'` |
| `AvailabilityClosure` | `"endsAt" > "startsAt"` |

Все пять ограничений входят в миграцию `20261121000000_init`. Сервер также проверяет вместимость выбранного стола и соответствие закрытия локальному дню или допустимому окну.

Личные запросы на чтение и изменение ограничиваются ID из проверенной сессии по `Booking.userId` или `Notification.recipientId`. Сервер перечитывает актуальную роль для защищённых действий. Для управления ролями он проверяет и актора, и целевой аккаунт. Пароль и хеш не возвращаются клиенту и не попадают в аудит. Связи в схеме обеспечивают целостность данных. Проверки прав и фильтрацию выдачи выполняет серверный слой на этапах 3–5.

## Расчёт доступности

1. Взять текущий момент по серверным часам. В зоне ресторана `Europe/Moscow` получить сегодняшнюю дату и следующие 13 календарных дат. Пользовательский часовой пояс не влияет на этот расчёт.
2. Для вторника–воскресенья сформировать локальные старты 12:00, 13:30, 15:00, 16:30, 18:00 и 19:30. Преобразовать в абсолютные моменты, прибавить 90 минут и проверить, что окно полностью до закрытия в 21:00. Оставить только старты строго позже текущего момента.
3. Убрать окна, пересекающиеся с `AvailabilityClosure`. Закрытый день хранится от локальной полуночи до следующей локальной полуночи. Закрытое окно хранится по границам соответствующего сеанса. Неактивные столы исключаются по `Table.isAvailable`.
4. Для оставшихся окон взять столы достаточной вместимости. Убрать кандидатов, занятых `pending` или `confirmed`. Интервалы пересекаются, если начало каждого строго раньше конца другого. Общая граница разрешена.
5. Публично вернуть только доступные окна для размера компании. При сохранении сервер заново проверяет всё и отдельно проверяет активные пересечения владельца. Стол выбирается по `capacity`, затем по `id`, оба в порядке возрастания. Если свободных столов больше нет, клиент получает конфликт и обновляет доступность.

Исключения хранятся отдельно от вычисленных окон, закрытия могут перекрываться, например одно окно внутри закрытого дня. При снятии закрытия удаляется только выбранное исключение. Чтобы закрыть дату, окно или стол, сервер сначала проверяет активные будущие брони по затрагиваемым интервалам. При конфликте закрытие отклоняется. `Table.isAvailable` действует до явного изменения. Интерфейс MVP не позволяет менять зону ресторана.

## Конкурентная защита

| Критерий | А. Exclusion constraints | Б. Serializable и повтор всей транзакции |
| --- | --- | --- |
| Одновременные запросы | PostgreSQL проверяет активные пересечения при записи, включая записи в обход Prisma. При конфликте одна запись отклоняется | PostgreSQL допускает только сериализуемый результат для участвующих транзакций. После конфликта сервер повторяет всю операцию с новым снимком, включая проверки и подбор |
| Prisma | Обычные чтения и записи доступны через клиент, ограничения не выражаются в Prisma Schema. Ошибку ограничения надо перевести в конфликт либо заново подобрать стол | Интерактивные транзакции Prisma ORM 7 поддерживают `Serializable`. Для конфликта сериализации или взаимной блокировки нужен ограниченный повтор, в Prisma это `P2034` |
| Ручной SQL и миграции | Нужна собственная миграция с `btree_gist` и двумя частичными ограничениями GiST по диапазону `tstzrange`. Проверяются доступность расширения и воспроизводимость миграции | Для защиты от пересечений достаточно Prisma-запросов и настройки изоляции. SQL `CHECK` для отдельных строк входят в начальную миграцию |
| Отмена | После коммита `cancelled` выпадает из предиката ограничения и освобождает интервал | Проверка читает только активные строки. После коммита отмены новая попытка видит слот свободным. Одновременная попытка может получить конфликт либо потребовать повтора |
| Один владелец | Отдельное ограничение по `userId` и пересечению диапазонов ловит и дубли, и разные старты | Запрос проверяет все пересекающиеся активные брони владельца, включая другой стол и другой старт, внутри той же транзакции |
| Один стол | Отдельное ограничение по `tableId` и пересечению диапазонов | Запрос проверяет активные пересечения кандидатов внутри той же транзакции, из которой создаётся бронь |
| Административные изменения | Ограничения действуют только на строки бронирований. Для закрытия окна или стола нужен дополнительный общий протокол | Один протокол покрывает создание и закрытия. Создание читает исключения и стол, закрытие читает затронутые брони перед записью. Обе операции выполняются в `Serializable` |
| Проверка на PostgreSQL 16 | Два подключения и конкурентные записи, включая прямой SQL для проверки самого ограничения | Два независимых подключения к тестовой БД через клиент, синхронизация после чтений, проверка отката, повторов и итоговых строк |

[Диапазоны и exclusion constraints в PostgreSQL 16](https://www.postgresql.org/docs/16/rangetypes.html#RANGETYPES-CONSTRAINT) · [Изоляция транзакций PostgreSQL 16](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-SERIALIZABLE) · [Транзакции Prisma ORM 7](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions) · [Возможности базы вне Prisma Schema](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/unsupported-database-features)

**Согласованный механизм MVP — вариант Б.** Все операции ниже используют единый серверный протокол с интерактивными транзакциями PostgreSQL уровня `Serializable`. Прямой SQL и сторонние писатели в обход протокола не получают гарантии от пересечений. Если появятся независимые писатели, вариант А можно рассмотреть как дополнительную защиту.

На каждой попытке сервер заново читает актуальную роль и проверяет право на действие и принадлежность ресурса, где это требуется. Все проверки выполняются внутри той же транзакции, что и запись. Создание брони, отмена владельцем и подтверждение сотрудником повторно проверяют дедлайн по серверным часам после записей брони, аудита и уведомления. При пересечении дедлайна все три записи откатываются. Граница относится к моменту финальной проверки, подтверждение `COMMIT` может прийти позже.

| Операция | Что проверяется заново перед записью |
| --- | --- |
| Создание брони | Горизонт, рабочий день, разрешённый будущий старт, длительность, число гостей, закрытия, состояние и вместимость столов. Проверяются пересечения активных броней владельца и стола. Стол заново выбирается по вместимости и ID. Бронь создаётся в `pending`. |
| Смена статуса | Текущий статус совпадает с ожидаемым, переход разрешён, выполнены условия по времени, роли, владельцу и причине. Обновление условно по ожидаемому статусу. При подтверждении сохраняется ранее назначенный стол. Устаревший запрос отклоняется. |
| Закрытие даты или окна | Интервал соответствует дате или допустимому окну в зоне ресторана. Точного дубликата закрытия нет. Нет пересекающихся активных будущих броней. |
| Открытие даты или окна | Выбранное закрытие существует и совпадает с ожидаемым интервалом и видом. Удаляется только оно. Остальные ограничения продолжают учитываться при расчёте доступности. |
| Отключение стола | Стол существует и сейчас доступен. Для него нет активных будущих броней. |
| Включение стола | Стол существует, сейчас отключён и имеет положительную вместимость. Включение меняет только флаг. Доступность каждого окна по-прежнему зависит от расписания, закрытий и броней. |

На операцию допускается максимум три попытки, включая первую. При `P2034` повторяется вся транзакция с новым снимком и новым серверным временем. Бизнес-конфликт завершает операцию без повтора. После третьей неудачной попытки сервер возвращает ошибку конкурентного изменения.

Аудит и связанные уведомления сохраняются атомарно с основным изменением. Создание брони и смена статуса пишут аудит и уведомление. Операции с закрытиями и столами пишут аудит. Ошибка любой связанной записи откатывает всю транзакцию.

## Переходы, атомарность и проверки

Все переходы из спецификации представлены перечислением и полями времени. При создании записывается `pending`. Из `pending` можно подтвердить до старта, отменить, завершить после конца с причиной или отметить неявку после конца. Из `confirmed` можно отменить, завершить или отметить неявку. Условия отмены проверяются по роли и серверному времени. Из терминальных статусов переходы запрещены. Перечисление ограничивает допустимые значения, а соответствие перехода правилам проверяется в серверной транзакции.

При смене статуса запрос передаёт `expectedStatus`. Сервис читает текущий статус, возвращает `409` при несовпадении, проверяет действие и выполняет условное обновление с ожидаемым статусом. При отсутствии обновлённой строки операция отклоняется. Непустая причина административной операции проверяется после удаления пробелов по краям. Нулевой символ в причине даёт `400` до записи. В той же транзакции создаются уведомление с новым статусом и запись аудита с предыдущим и новым значением и причиной при необходимости. Ошибка на любом шаге откатывает все записи. Смена роли и её аудит также атомарны. Роль на момент действия сохраняется отдельно от текущей роли аккаунта.

Офлайн-проверки запускаются через `npm exec -- prisma format --check`, `npm exec -- prisma validate` и `npm exec -- prisma generate` без `DATABASE_URL`. Prisma CLI и seed загружают `.env`. Сгенерированный клиент не отслеживается. Seed использует адаптер `@prisma/adapter-pg` и выставляет UTC для своего соединения, чтобы сохранять точные моменты независимо от часового пояса PostgreSQL.

## Миграция и seed

Инициализация отдельной базы и команды применения миграции описаны в [README проекта](../README.md#локальный-запуск). Миграция `20261121000000_init` создаёт шесть согласованных таблиц, перечисления, индексы, внешние ключи и пять SQL `CHECK`. Миграция `20261121010000_add_sessions` добавляет таблицу `Session`, индекс владельца и каскадный внешний ключ.

Seed добавляет:

| Данные | Состав |
| --- | --- |
| Аккаунты | `super-admin@verde-marea.test` (`super_admin`), `admin@verde-marea.test` (`admin`), `user@verde-marea.test` (`user`) |
| Столы | `Demo 01`–`Demo 04`, вместимость 2, 2, 4 и 6 |
| Доступность | Одно историческое закрытие окна 6 января 2026 года с 12:00 до 13:30 по Москве |

Seed берёт пароли из трёх переменных `SEED_*_PASSWORD`, хеширует их через bcryptjs с cost 12 и добавляет только отсутствующие строки в одной транзакции. Повторный запуск сохраняет существующие роли, хеши, столы и исключения. Брони, уведомления и аудит для проверки связей создаются только в SQL-проверке с откатом.

## Безопасное обновление

1. Проверь, на какую базу указывает `DATABASE_URL` в окружении запуска. При изменении схемы сделай резервную копию этой базы, например через `pg_dump`, и сначала проверь миграции на отдельной тестовой базе. Держи резервную копию вне Git.
2. Останови текущий экземпляр приложения. Из корня обновлённой копии выполни:

   ```sh
   npm ci
   npm exec -- prisma generate
   npm exec -- prisma migrate deploy
   npm exec -- prisma migrate status
   ```

   Для обновления только серверной логики достаточно установки по lockfile и генерации Prisma Client. Миграции нужны при наличии новых миграций схемы. Seed выполняй отдельно, когда нужно добавить демонстрационные данные.
3. Проверь TypeScript и ESLint. Для production-запуска собери приложение командой `npm run build -- --webpack` и запусти через `npm start`. Для локального запуска используй `npm run dev -- --webpack`. Проверь бронирование и вход по [чек-листу](../README.md#чек-лист-локальной-приёмки).
4. Если миграция завершилась с ошибкой, оставь приложение остановленным, проверь `prisma migrate status` и разберись с причиной на отдельной базе. Сохрани резервную копию до завершения проверки.

## Сброс одноразовой демонстрационной базы

**Сброс удаляет все данные выбранной схемы, включая аккаунты, сессии, брони и аудит.** Для этой процедуры используй отдельную локальную базу `verde_marea_reset_test`. Храни рабочие данные в другой базе. Если данные нужны, сделай резервную копию. Останови приложение, подключённое к одноразовой базе, перед сбросом.

Создай базу через `createdb` по примеру [локального запуска](../README.md#локальный-запуск), заменив имя базы на `verde_marea_reset_test`. Подготовь три пароля seed в локальном `.env` или окружении процесса. Задай `RESET_TEST_DATABASE_URL` в текущей оболочке как URL именно одноразовой базы. Выполни блок в интерактивном терминале:

```sh
(
  set -eu
  export DATABASE_URL="${RESET_TEST_DATABASE_URL:?Укажи URL одноразовой базы}"
  node -e '
    const url = URL.parse(process.env.DATABASE_URL);
    if (!url || !["postgresql:", "postgres:"].includes(url.protocol)
        || !["127.0.0.1", "localhost", "[::1]"].includes(url.hostname)
        || url.pathname !== "/verde_marea_reset_test" || url.search || url.hash) {
      console.error("Нужна локальная verde_marea_reset_test без параметров URL.");
      process.exit(1);
    }
  '
  npm exec -- prisma migrate reset
  npm exec -- prisma db seed
  npm exec -- prisma migrate status
)
```

Перед подтверждением в Prisma сверь имя сервера, базы и схемы. `migrate reset` заново применяет миграции. Следующая команда отдельно заполняет базу демонстрационными данными. Переменная для сброса действует в показанном блоке, поэтому обычная конфигурация приложения сохраняется.

### Проверка на отдельной базе

Создай пустую `verde_marea_test` тем же способом, что и локальную базу. Укажи это имя в `DATABASE_URL` и выполни команды миграции, генерации клиента и seed из README. Затем выполни:

```sh
psql -X -h 127.0.0.1 -U YOUR_DB_USER -d verde_marea_test -f prisma/verify-schema.sql
npm exec -- prisma db seed
npm exec -- prisma migrate status
```

При нестандартном порте укажи его и в URL, и в команде `psql`. Скрипт проверяет пять `CHECK`, внешние ключи, уникальность и корректные связи. Все его тестовые записи откатываются. Повторный seed на подготовленной базе должен сообщить о вставке нуля строк.

Конкурентные записи, гонки с управлением доступностью, отказ при устаревшем статусе, откаты и временные границы проверяются в интеграционных наборах. Для полного запуска используй отдельные базы без seed по [инструкции строгой проверки](../README.md#строгая-проверка-перед-сдачей).
